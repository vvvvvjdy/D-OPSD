# Troubleshooting D-OPSD Adaptations

Use the [migration workflow](migration.md) to establish a native baseline and zero-shot teacher examples. Diagnose problems using the exact checkpoint, context, preprocessing, and sampling settings used by the adaptation.

## Teacher context does not improve the desired behavior

First inspect the zero-shot teacher output before training. Hold the checkpoint, sampler, step count, time values, guidance, output size, and seed/initial noise fixed; change only the conditioning.

Check that the model supports the chosen reference format, the prompt identifies image roles clearly, and the image information actually reaches the intended conditioning path. For multi-image context, verify image order, image IDs, masks, and any truncation. Try a context formulation the model can interpret more reliably.

Adding a target image does not by itself ensure a better teacher. The older Qwen editing model discussed in [issue #9](https://github.com/vvvvvjdy/D-OPSD/issues/9) is one example of this concern. Useful new context designs can use extra text, images, or other modalities supported by the model; share ideas and results in [Issues](https://github.com/vvvvvjdy/D-OPSD/issues).

## Outputs zoom in or change framing

Inspect the teacher at step zero using the exact D-OPSD conditioning, including the teacher prompt and all reference/target images. Compare normal conditioning with the proposed teacher conditioning under the same inference settings.

Also save the images after preprocessing. Resize-to-fill followed by center cropping can change framing, and a multi-reference context can introduce its own composition bias. If that bias is already present in the teacher, the student can learn it quickly.

A teacher LoRA that looks good under ordinary source-only inference should also be checked under the actual D-OPSD teacher context and on student states. See [issue #10](https://github.com/vvvvvjdy/D-OPSD/issues/10).

## Image conditioning appears to be ignored

Verify that the intended vision and connector weights loaded, and inspect missing/unexpected keys rather than relying only on a successful forward pass. Check image preprocessing, selected hidden-state layers, masks, and whether image tokens survive sequence truncation.

For the Z-Image VLM construction, preserve compatibility with the diffusion model's text-conditioning space. The public implementation uses the pipeline text encoder's language weights together with the visual components; substituting an arbitrary VLM with the same feature dimension is not enough to establish compatibility.

In [issue #8](https://github.com/vvvvvjdy/D-OPSD/issues/8), a vision-weight key mismatch caused the failed reproduction. [Issue #2](https://github.com/vvvvvjdy/D-OPSD/issues/2) discusses the multimodal encoder construction.

## The code uses x_0 MSE while the paper describes velocity alignment

The public code aligns the predicted clean latents from the teacher and student at the same state. With `x_0 = x_t - t*v`:

```text
x_0_student - x_0_teacher = -t * (v_student - v_teacher)
MSE(x_0_student, x_0_teacher) = t^2 * MSE(v_student, v_teacher)
```

The corresponding expression under the Z-Image example's time direction uses `(1-t)^2`. This gives time-dependent weighting of velocity alignment. The authors recommend predicted `x_0` MSE as the default, following the public implementation. See [issue #6](https://github.com/vvvvvjdy/D-OPSD/issues/6).

Check the target model's own conversion formula. Also check that the loss compares matching generated positions, rather than including extra reference tokens or comparing to the dataset's GT latent.

## Loss decreases but few-step quality worsens

Trace one training rollout. Verify that the states are generated by the current student, both branches predict on the same state/time, and the student prediction drives the next state. Inspect the actual sampler array, output parameterization, teacher guidance, and clean-latent conversion.

Check that teacher outputs are detached and that the teacher update uses the intended EMA value. The recommended decay is **0.9999**; a fixed teacher is an alternative. In the public scripts, the recommended value is passed explicitly and differs from the argument parser's default.

Then inspect the teacher predictions and adjust LR or training duration based on fixed-example generation results. [Issue #3](https://github.com/vvvvvjdy/D-OPSD/issues/3) discusses the importance of supervision on the model's own rollout states. [Issue #7](https://github.com/vvvvvjdy/D-OPSD/issues/7) includes discussion of teacher-trajectory alignment; keep it distinct from evaluating the teacher on student states.

## Training runs, but the intended parameters do not learn

Inspect the active adapter, optimizer parameter groups, `requires_grad` flags, and gradients after backward. Confirm that the intended student parameters change after an optimizer update. For shared-base dual adapters, also verify the adapter active during gradient-checkpoint recomputation.

Check whether gradients were inadvertently disabled for the student path or the entire loss. Keep teacher targets detached while retaining the student prediction's computation graph.

## Full fine-tuning is unavailable in the example script

The public entry points currently raise `NotImplementedError` for their full fine-tuning branch. The D-OPSD procedure remains the same, but the implementation must train full student parameters and maintain the corresponding teacher parameter state. See [issue #11](https://github.com/vvvvvjdy/D-OPSD/issues/11).

Start with an LR 5–10 times lower than the corresponding LoRA LR, as described in [the recommendations](recipes.md#learning-rates-and-lora-settings). For sharded execution, implement EMA and checkpoint handling against the distributed framework's parameter/state representation.

## GPU memory is insufficient

Identify whether the peak comes from parameters, activations, encoders, or optimizer state. The existing ZeRO-2 setup does not shard model parameters, so additional data-parallel GPUs may leave the main bottleneck unchanged.

Consider FSDP2 or ZeRO-3 for parameter sharding; use smaller micro-batches, gradient checkpointing, or valid precomputation for other bottlenecks. Account for teacher parameters during full fine-tuning and for extra context length in teacher forwards. Follow [the memory guidance](migration.md#6-adapt-memory-use-and-distributed-execution).

## The exported student behaves differently from training previews

Confirm that the export/load path selects the student weights or adapter. Compare model and library versions, preprocessing, prompt handling, guidance, and the actual timestep/sigma arrays used in the preview and native inference.

Run a fresh load using only the student's normal task inputs. The final inference workflow can remain unchanged apart from loading the trained weights or LoRA. Teacher-only references or target-derived prompts should not be required.

## Discussing a new adaptation

We welcome questions, new teacher-context ideas, and community implementations in [GitHub Issues](https://github.com/vvvvvjdy/D-OPSD/issues).

Useful details include the exact model and library versions, task, a sample's field/conditioning mapping, teacher prompt and reference order, sampling time values and guidance, EMA and LR, and a few baseline/zero-shot-teacher/trained-student comparisons. For an implementation error, include a minimal reproducer or relevant traceback. These details make it easier to distinguish context behavior from sampler, data, or training issues.
